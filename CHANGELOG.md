## 0.2.0

- Added a Golden Matrix Runner (FEAT-69, `test/support/golden_matrix.dart` — test-only, not exported: it depends on `flutter_test`, a dev_dependency this package doesn't ship): `runGoldenMatrix(tester, builder, {goldenBaseName, matrix, guidelines})` pumps a widget through a bounded, deterministic sweep (`defaultGoldenMatrix`: baseline + 1 variation per axis — dark, `vi` locale, RTL, 2 text scales, reduced motion — 7 cases total, not a full cartesian product) and fails on `tester.takeException()` (overflow/render error) or a broken `androidTapTargetGuideline`/`labeledTapTargetGuideline` (Flutter's own built-in accessibility guideline matchers, reused rather than reimplemented), optionally diffing each case against a deterministically-named `<goldenBaseName>_<case.name>.png`. Demonstrated end-to-end against `CommonButton` (`test/widget/goldens/common_button_matrix_golden_test.dart`, 7 real golden PNGs) — applying it to the rest of the ~47-widget kit is left as follow-up work, not done in this task.
- Fixed `CommonButton`'s pill height: content-driven height landed at 47.0px, 1px under Android's 48dp minimum tap target — found by the Golden Matrix Runner's `androidTapTargetGuideline` check while building it (real payoff of the new tool, not a review finding). Fixed with `constraints: BoxConstraints(minHeight: 48)`; `ShopItemCard`'s golden fixtures (the only other golden-tested widget embedding `CommonButton`) regenerated to match.
- Added `validateNeonThemeContrast`/`ContrastCheck`/`ContrastIssue`/`ThemeContrastConfig` (FEAT-68): a WCAG contrast validator for `NeonTheme` — checks `ink`/`inkSoft` on `card`/`cardAlt` (normal-text threshold, default AA 4.5:1), `muted` on `card`/`cardAlt` (a sanity-only "not literally invisible" check, since WCAG exempts disabled controls from a real contrast bar), `lockedBorder` on `lockedFill` (UI-component threshold, default 3.0:1), and every pair of `NeonTheme.gemColors` (an RGB-distance heuristic, not a real CVD simulation) across both `dark` states and both `colorBlindSafe` states — restoring both flags afterward, so calling it never leaves the live theme mutated. `validateNeonThemeContrastPairs` is the underlying pure function (plain `ContrastCheck` colors in, no `NeonTheme` dependency), for validating a candidate reskin before importing it. Found 2 real, pre-existing issues in the current palette while building this (documented, not fixed, in this task's `doc/task/done/FEAT-68-theme-contrast-validator.md`): `inkSoft` on light-theme `card`/`cardAlt` reads at 3.92:1/3.40:1 — under the 4.5:1 AA bar for normal text, though over the 3.0:1 large-text/UI bar — and `lockedBorder`/`lockedFill` reads at 1.43:1 regardless of `dark`, since neither token has a separate dark variant. No CLI tool ships for this one: unlike `tool/economy_sim.dart`/`tool/api_compatibility.dart`, a real check needs `NeonTheme`'s actual `Color` values, and `NeonTheme` transitively imports `dart:ui` — unavailable to a plain `dart run` process outside the Flutter engine (confirmed by trying it: `Error: Dart library 'dart:ui' is not available on this platform`) — so this validator's CI coverage lives in `flutter test` instead, which is already a CI step.
- Added `InventoryGrid` (FEAT-56): a data-driven grid over an `InventorySnapshot` (FEAT-44) — `itemBuilder` is entirely caller-supplied (this package ships no concrete item catalog/renderer), and a tap/drag never mutates anything; the caller's own handler is expected to call `InventoryService.consume`/`setEquipped`/`moveSlot` itself. Cells beyond `snapshot.slots.length` render as empty up to an optional `unlockedCapacity` (default: no locked cells at all), then locked beyond that — `InventorySnapshot` itself has no "locked" concept, this is a presentation-only opt-in. Built on `GridView.custom` with an explicit `SliverChildBuilderDelegate.findChildIndexCallback` keyed by `InventorySlot.slotId` — `GridView.builder`'s plain delegate has none, so Flutter's sliver reconciliation only compares "the widget now at index N" against whatever Element previously sat at index N and never searches the rest of the list for a matching key; without `findChildIndexCallback`, a reorder or a removal that shifts a slot to a different index would silently hand its old Element/State to whatever item now lands at that index instead of following its own `slotId` — caught by a widget test using a stateful item builder before this shipped, not by inspection. Supports drag-to-reorder via `onReorder(fromSlotId, toSlotId)` (also opt-in, disabled by default) built on `Draggable`/`DragTarget`.
- Added `LevelUpOverlay`/`LevelUpOverlayController`/`LevelUpCelebration` (FEAT-54): a data-driven level-up celebration overlay — the caller supplies `LevelUpEvent`s already obtained from `PlayerProgressionService.grantXp` (FEAT-43); this widget only presents them, it never calls `grantXp`/`RewardTransactionPipeline` itself. Sequences `xpFill → levelPop → rewardReveal` per queued level, in ascending order, then either moves to the next queued level or back to `idle`. `LevelUpOverlayController` is a pure Dart, token-guarded state machine (same shape as `SceneTransitionController`, FEAT-58) — every `show()` mints a token, and only that token's continuation may mutate state, so a superseded `show()` silently drops its own late completion instead of double-firing `onComplete`. `skip()` jumps straight to `idle` and fires `onComplete` (once, guarded the same way) instead of waiting out the remaining phases — implemented with a real cancellable `Timer` per phase (not `Future.any([Future.delayed(...), ...])`, which never cancels its losing branch and would otherwise leave a real pending timer alive after an early skip). Confetti (reusing `ConfettiOverlay`) and haptic feedback are both optional and automatically skipped under reduced motion.
- Added `AdaptiveGameHud`/`HudSlot`/`HudBreakpoint` (FEAT-52): a HUD-content placement widget that reserves `topStart`/`topCenter`/`topEnd`/`bottom`/`side`/`overlay` slots without a caller hand-rolling safe-area, notch, keyboard-inset, RTL, and breakpoint handling itself. Every edge slot is padded by `MediaQueryData.padding` directly (never wrapped in `SafeArea`, which would apply the same inset to every slot even when only one edge needs it); `bottom` additionally clears `viewInsets.bottom` so an on-screen keyboard never covers it. `topStart`/`topEnd`/`side` use Flutter's own `PositionedDirectional`, so RTL swaps sides automatically with no custom logic. `HudSlot.side` hides entirely below `compactBreakpointWidth` (width-driven, not orientation — an orientation change already changes width, so a separate check would just be a second source of truth for the same decision); a descendant of any slot can read the resolved `HudBreakpoint` via `AdaptiveGameHud.breakpointOf`. An optional `flameViewportBounds` (local coordinates) keeps the top/bottom slots outside Flame's actual visible viewport when the game's camera doesn't fill the widget (fixed-aspect-ratio letterboxing) — deliberately vertical-only, since horizontal letterboxing would need to reconcile with RTL start/end and is rare on phones. Never wraps `slots` in its own `Obx`/`GetBuilder`, so a slot's own reactive content rebuilds independently of the HUD itself.
- Added `ObjectPool`/`PooledComponent` (FEAT-48): a generic acquire/release object pool for reusing allocation-heavy instances (Flame particles/projectiles) in a hot gameplay loop instead of allocating and discarding one every frame. `release()` throws `StateError` on a double-release or a foreign object this pool never handed out — identity, not `==`, decides what's currently active, so a `T` overriding equality can't confuse the check. `maxCapacity` bounds what `release()` retains (`prewarm()`/normal reuse), never what `acquire()` can hand out — a burst past capacity still succeeds, just without retaining the surplus past its next release. `PooledComponent` is a Flame `Component` mixin that calls back into its pool automatically from `onRemove()`, via a plain `void Function()` callback (`attachToPool`) rather than holding a typed `ObjectPool<T>` reference, sidestepping Dart's invariant generics entirely. `tool/object_pool_benchmark.dart` (headless, no Flutter/Flame dependency, cross-checked in `test/tool/object_pool_benchmark_test.dart`) runs a representative particle-burst scenario through the real `ObjectPool` class and prints its allocation reduction versus an unpooled baseline — a pool sized smaller than the scenario's concurrent-alive working set shows zero reduction by design (every release lands past capacity and gets disposed), which the benchmark's own test suite locks in as intended behavior rather than a bug.
- Added `OfflineOutboxService`/`OutboxItem`/`ConflictPolicy`/`SyncOutcome`/`ManualResolution` (FEAT-67): a persisted, priority-drained outbox for syncing local changes to a remote authority once back online, built on `RetryExecutor` (FEAT-35) for transient-failure backoff and, when a `ConnectivityCoordinator` (FEAT-62) is supplied, driven automatically by its online transitions the same way that service drains its own internal task queue. An item is persisted from `enqueue()` until the exact call that removes it *also* persists that removal, so a crash between the remote authority accepting an item and this service recording that leaves the item still queued for the next `drain()` — it always retries with the *same* `OutboxItem.idempotencyKey`, so nothing is ever silently lost; avoiding a duplicate effect on the remote side is the injected `OutboxUploader`'s own responsibility (a real backend keys on that same id to dedupe a retried request it already applied). `enqueue()` only auto-drains when a `ConnectivityCoordinator` confirms it's online right now — without one, back-to-back `enqueue()` calls would otherwise race their own fire-and-forget drain attempts against each other and break the priority ordering a single `drain()` call guarantees. A `SyncConflict` response is handled per `ConflictPolicy`: `reject` discards the local change for *that sync attempt only* (it never reaches back into wherever the change came from — a wallet, an inventory — to undo it, so nothing already granted locally is lost); `merge` calls a required `ConflictMerger` and re-uploads once more, falling back to `manual` instead of looping forever if that still conflicts; `manual` parks the item in `manualReviewItems` (with the authority's `remotePayload` attached) until `resolveManual` picks `ManualResolution.keepLocal` (re-queues the original payload) or `acceptRemote` (drops it). A corrupt save resets to an empty outbox instead of throwing, the same fail-safe posture as this kit's other ledger-style services.
- Added `InventoryService`/`ItemDefinition`/`InventorySlot`/`InventoryLine`/`InventorySnapshot` (FEAT-44): a generic slot-based inventory (consumables + equipment) built on the same idempotent-ledger pattern as `EconomyWallet` (FEAT-31)/`RewardTransactionPipeline` (FEAT-42) — every mutating call (`grant`, `consume`, `setEquipped`, `moveSlot`) runs under `AsyncActionGuard.runExclusive('inventory', ...)`, so concurrent calls serialize deterministically instead of racing, and a repeated `transactionId` on `grant`/`consume` (even across a restart) is a no-op. A `grant`/`consume` call takes a list of `InventoryLine`s and applies them **atomically** against a scratch copy first — if any single line would exceed `capacity` (grant) or ask for more than is on hand (consume), the whole call is rejected and *none* of the lines mutate the real inventory, not just the failing one. `grant` fills existing under-`maxStack` stacks of the same item before opening a new slot. `ItemDefinition` is entirely caller-supplied (no concrete item list baked into the kit) — an unknown item id in a `grant` line is rejected before any mutation, and a persisted slot referencing an item id no longer in the current catalog (a stale save from before an item was removed/renamed) is silently dropped on load rather than crashing or granting a replacement; a fully corrupt save resets to an empty inventory the same way `EconomyWallet` does. `setEquipped`/`moveSlot` are naturally idempotent (no transaction id needed) and target a slot's stable `slotId`, which survives other slots shifting around from a grant/consume elsewhere in the same inventory.
- Added `PlayerProgressionService`/`LevelDefinition`/`PlayerProgressionSnapshot`/`LevelUpEvent` (FEAT-43): a versioned XP/level SSOT built on the same idempotent-ledger pattern as `EconomyWallet` (FEAT-31) and `RewardTransactionPipeline` (FEAT-42) — `grantXp(amount, transactionId)` runs under an `AsyncActionGuard.runExclusive` key, so concurrent grants serialize instead of racing, and a repeated `transactionId` (even across a restart) is a no-op that returns the current snapshot rather than double-counting. `level`/`xpIntoLevel`/`xpToNextLevel` are never persisted directly — only lifetime `totalXpEarned` is, and the rest is always re-derived from it against the curve (pure `levelForTotalXp`/`xpIntoLevelForTotalXp`), so they can never drift out of sync with a curve change. `validateLevelCurve` rejects a broken `LevelDefinition` list (duplicate/missing level number, a non-final level with `xpToNext <= 0`, a decreasing curve, or cumulative XP overflowing the supported range) at construction time — a bad config throws `ArgumentError` immediately rather than producing silently-wrong level math later; the curve's last entry must have `xpToNext == 0`, which is what marks the max level. A `grantXp` call that crosses several level thresholds at once (a big XP grant, an offline-earnings catch-up) grants each newly-reached level's `unlockRewardLines` exactly once through an injected `RewardTransactionPipeline` (deterministic `'level_up:$level'` transaction id) and fires `onLevelUp` once per level in ascending order; XP past the curve's max level is still tracked in `totalXpEarned` for analytics honesty, but `level` itself is capped and no further unlock fires. A corrupt/malformed save resets to a fresh level-1 state (never throws, never trusts a partially-decoded value upward) — same fail-safe posture as `EconomyWallet`'s own hydrate.
- Added `SceneTransitionController`/`SceneTransitionOverlay`/`SceneTransitionPhase` (FEAT-58): a token-guarded scene-transition state machine (`idle → covering → loading → revealing/error → idle`) plus the in-tree overlay widget that renders it — same `NeonDialog`-style in-tree-overlay pattern (works over a full-screen Flame `GameWidget`, where `Navigator`/`showDialog` can't). The controller is pure Dart (no `Animation`/`BuildContext`), unit-tested as a state machine before any animation code was written: every `run()` mints a token, and only that token's continuation may mutate `phase`/`progress`/`lastError` — a still-in-flight `run()` superseded by a newer one (rapid re-navigation), or one still resolving after `cancel()`/`dispose()`, silently drops its own late completion instead of stomping the current state or leaving a stuck pointer-blocking barrier. `progress` only reflects the active transition. On failure, the overlay shows `RetryErrorState.fromSdkFailure` wired to an optional `onRetry`; the underlying scene is `ExcludeSemantics`+`IgnorePointer`-guarded for the whole time the transition isn't `idle`, so a stray tap/screen-reader focus can never reach the scene being replaced, and the barrier releases the instant `phase` returns to `idle`. Respects `MediaQuery.disableAnimations` (or an explicit `reducedMotion` override) by collapsing the cover/reveal fade to zero duration instead of animating. `runWithAssetPreload` wires the controller directly to a real `AssetPreloadCoordinator` (FEAT-47) + `GameSessionController` (FEAT-41): preload progress feeds `progress`, and a successful preload calls `markReady()`+`start()` on the session so the transition and session phase land in sync.
- Added `AssetPreloadCoordinator`/`AssetManifestItem`/`AssetKind` (FEAT-47): a typed, dependency-aware asset preloader — no concrete Flame/audio/Flutter-asset/shader API baked in, a consuming app injects a `loader`/`unloader` function pair that dispatches on `AssetManifestItem.kind`. `preload()` validates the manifest up front (a `dependsOn` referencing a missing id, or a dependency cycle, both return a typed `SdkFailure(kind: validation)` before any loader call runs, via DFS 3-color cycle detection). Items load in dependency-ordered waves, each wave bounded by `maxConcurrent` in-flight loader calls. `progress` (0.0–1.0, exposed as a `RxDouble`) only advances for an item that finishes in a way that lets the scene proceed — success, or an optional item's failure; a required item's failure (and everything that transitively depends on it, propagated through the wave graph) is excluded, so `progress` can never falsely reach 1.0 while a required asset is missing — a caller must check the returned `SdkResult`, not just watch for `progress == 1.0`. An item id already loaded by an earlier `preload()` call is never loaded twice — the coordinator tracks a reference count per id, `unloadScene()` decrements it for the last-preloaded manifest and only calls `unloader` once a shared asset's count reaches 0 (so 2 scenes sharing one background texture don't unload it out from under each other). `cancel()` stops starting new waves but never abandons an in-flight loader call (nothing leaks); `retryFailed()` simply re-runs `preload()` against the last manifest — the same cache naturally skips everything already loaded, so only the previously-failed items (and anything they blocked) actually re-attempt.
- Added `PluginAdapterConformanceSuite`/`ConformanceReport` (FEAT-66): a shared conformance checklist a consumer runs against their own concrete implementation of this kit's platform-neutral seams (`AnalyticsProvider`, `CloudSaveProvider`, `SecureStorageAdapter`, `CrashReporter`, `PurchaseSeam` — no "ads" adapter, since this kit ships no ads mediation seam by product decision) without importing any vendor SDK. Every check is independent and never throws itself — a check that would have thrown is recorded as a `false` result instead, so one broken check never aborts the rest of the checklist. Every check (including plain "does not throw" ones) is bounded by a per-call `timeout`, so a hanging adapter can never block the checklist regardless of which check catches it first — found and fixed exactly this bug during TDD (an earlier version only timeout-guarded the checks explicitly testing for timeout, so a hung adapter blocked an unrelated "does not throw" check for the full 30s test-runner timeout instead of failing fast). `SecureStorageAdapter`'s checklist includes a real privacy check: `delete`/`clear` must leave no residual readable value, not just "not throw". Ships `FakeCloudSaveProvider`/`FakeCrashReporter`/`FakePurchaseSeam` (in-memory reference implementations, alongside the existing `FakeSecureStorageAdapter`/`NoopAnalyticsProvider`) that pass their own suite and double as example implementations.
- Added `PlatformCapabilityRegistry`/`PlatformCapabilitySnapshot`/`detectPlatformCapabilities` (FEAT-71): a typed, cached capability snapshot (haptics/shaders/notifications/background audio) for Android/iOS/web/desktop, computed once from `kIsWeb`/`defaultTargetPlatform` — no platform channel calls beyond what Flutter itself already resolves at process start. Ships a documented, deliberately conservative compatibility policy (every capability assumed unsupported on web; haptics also assumed unsupported on desktop, since there's no OS haptic API there) rather than a hard platform fact — a consumer that knows better for its target can construct the registry with an explicit override snapshot. `withFallback` gives call sites an explicit, testable fallback policy instead of silently skipping or crashing on an unsupported platform; a real error thrown by either branch still propagates normally. `detectPlatformCapabilities`'s `isWeb`/`targetPlatform` params are injectable, so its device-matrix test fixtures every platform combination without needing a real device per platform. Demoed in `WidgetShowcaseScreen`, including a "fire haptic with fallback" button.
- Fixed `CommonButton` pills having **zero horizontal padding** — long labels could visually touch/crowd the pill's rounded edges instead of having proper inset. Added `horizontal: NeonTheme.s16` alongside the existing vertical padding; regenerated the 2 golden images this shifted (`shop_item_card_basic.png`/`shop_item_card_ribbon.png`).
- Added `AppSessionTracker`/`SessionInfo` (FEAT-63): session id, install/session-sequence counters, and foreground duration in one place instead of every feature hand-rolling its own bookkeeping. One session per process — `sequence` increments exactly once per construction (cold start); a hand-edited/corrupt negative persisted sequence clamps to 0 before incrementing, never propagating a negative value forward. Foreground duration is measured with an injectable `Stopwatch` (real elapsed time, not wall clock — a duration measurement doesn't care about clock anomalies) and excludes backgrounded time entirely. A resume within `sessionTimeout` (default 30 min) of backgrounding continues the same session; a resume after longer starts a brand new one (new `sessionId`, bumped `sequence`, foreground duration reset) — the standard mobile-analytics "session timeout" convention. `analyticsContext()` returns `{}` unless `ConsentCategory.analytics` is currently granted on the registered `ConsentStateService` (FEAT-61) — the tracker never sends anything itself, but a caller attaching this to an analytics event can't leak session/install data pre-consent. Demoed in `WidgetShowcaseScreen`.
- Added `AppVersionGate`/`GateDecision`/`AppVersionGateConfig`/`evaluateVersionGate`/`compareAppVersions`/`AppVersionGateController` (FEAT-59): soft/force update and maintenance-mode gating from remote config, with a fully safety-first policy — any invalid input (an unparseable current version, or an unparseable `minimumVersion`/`recommendedVersion`) degrades to `GateDecision.ok` rather than ever force-blocking a user for a corrupt config; only a plain `maintenanceActive` bool (can't be "invalid") can force/maintenance-gate. `compareAppVersions` documents its own semver policy: prerelease sorts before the same core release (`1.2.3-beta` < `1.2.3`), build metadata (`+001`) is ignored entirely. `AppVersionGateController` reads straight from `RemoteConfigService` rather than keeping its own cache — that service already gives "asset default, remote merges in, remote fail/corrupt keeps last-good" for free (`ENH-58`). Ships `AppVersionGateOverlay`: force/maintenance block the back button (`PopScope(canPop: false)`) and aren't dismissible; soft update is dismissible and reports back via `onSoftDismiss` so the caller can persist the cooldown; a failed injected `launchStore` call shows an inline error and a "Retry" button instead of looping. Demoed in `WidgetShowcaseScreen`.
- Added `DeepLinkCommandRouter`/`DeepLinkRoute`/`DeepLinkCommand`/`parseDeepLink` (FEAT-60): parses deep links into typed commands against an allowlist of routes (scheme/host/path shape — a `:name` path segment captures a param) and dispatches them to registered handlers, with no concrete deep-link plugin dependency — a consuming app feeds its own URI stream (e.g. `app_links`) into `handleUri`. `parseDeepLink` is a pure function (fixture-testable) that rejects an oversized URI, an unrecognized scheme/host, or a path that matches no route — never throws. A link arriving before `markReady()` is queued (never dropped) and drains exactly once when the app signals it's ready; a duplicate call for the same URI within `dedupeCooldown` is ignored, deterministically even for 2 concurrent calls (the cooldown is stamped before any handler awaits). Every handler registered for a command type runs (highest `registerHandler` priority first) even if an earlier one throws — captured per-entry in a diagnostic `DeepLinkHandlerResult`, never rethrown, and never affecting a different command's dispatch. Demoed in `WidgetShowcaseScreen` and wired into the example app's real `AndroidManifest.xml` intent-filter (`roycasualkit://open/...`) via `app_links`.
- Added `ConnectivityCoordinator`/`ConnectivitySignal`/`ConnectivityState`/`QueuedTask` (FEAT-62): a reactive Internet-reachability coordinator with a bounded, idempotent retry queue. `ConnectivityState.online` is reported **only** once an injected `probe` (e.g. a HEAD request to a known-good endpoint) actually succeeds — a `ConnectivitySignal` reporting a network interface is up is never, by itself, treated as online (a captive portal or DNS outage would otherwise false-positive). Interface flapping is debounced before evaluation, and a single failed probe while previously online moves to `ConnectivityState.degraded` rather than straight to `offline` (hysteresis) — only `failuresToGoOffline` consecutive failures declare it truly offline, so flapping connectivity can't spam the UI. `enqueue`d tasks are capped at `maxQueueSize` (evicts the lowest-priority entry once full), keyed by `idempotencyKey` (a duplicate replaces, never duplicates), and drain automatically once back online — highest priority first, through an injectable `RetryExecutor`/`RetryPolicy` (FEAT-35) per task; one task exhausting its retries is dropped without blocking the rest of the queue, and a mid-drain drop back offline stops the drain immediately, leaving the rest queued. `connectedStream` bridges directly into `NetworkStatusBanner.stream`. Timers use the same injectable `createTimer` seam as `CheckpointCoordinator`/`HapticChoreographer`, and `onClose()` cancels every timer/subscription — no leaks. Demoed in `WidgetShowcaseScreen` alongside a `FakeConnectivitySignal` test double.
- Added `ConsentStateService`/`ConsentCategory`/`ConsentStatus` (FEAT-61): an SSOT for privacy consent gating `analytics` and `personalization` (no `ads` category — this kit ships no ads mediation seam, a deliberate product decision from FEAT-02's rejection). **Default-deny**: a category never explicitly decided reads as `ConsentStatus.unknown`, never `granted`, and a corrupted or hand-edited persisted entry is dropped rather than coerced, so it also reads as unknown — never an accidental early unlock. `policyVersion` support: a category persisted under an older policy version reads back as `unknown` regardless of its prior decision, forcing a fresh review after a privacy-policy bump. `grant`/`deny`/`reset` persist immediately and take effect immediately within the same instance. Ships `ConsentGatedAnalyticsProvider`, a decorator over any real `AnalyticsProvider` that only forwards `logEvent` while analytics consent is granted — a consuming app registers it in place of its real provider so every call site automatically respects consent. Demoed in `WidgetShowcaseScreen`, including gating `ExperimentBucketingService`'s variant assignment behind personalization consent.
- Added `PersistentCooldownService`/`CooldownStatus`/`CooldownSnapshot` (FEAT-36): a keyed cooldown tracker (reward claim timers, booster reuse delays, PvP action gates, ...) that survives app restart and resists clock-rewind cheating — every read is computed lazily from `nowMsClamped()` against a persisted `key -> endMs` map, the same anti-cheat clamp `EnergyService`/daily rewards/streaks already use. There is deliberately **no timer of any kind** in the service, per-key or shared: N active cooldowns cost zero background timers, the same zero-timer design `EnergyService` already uses for its own regen math. `start`/`cancel` validate their input (empty key, non-positive duration) and persist immediately (not write-behind-buffered, since a missed write on kill would let a booster be reused for free); a corrupted or hand-edited per-key entry is dropped rather than trusted, so it reads as never-started instead of coercing into an early unlock. Ships `CooldownCountdownChip` (`presentation/widgets/common/`), a thin adapter over `CountdownChip` that takes plain `remaining: Duration` data (same convention as `EnergyBar`/`LevelSelectGrid` — widgets take data, the caller owns the GetX service) and renders nothing while a cooldown is ready.
- Added `DeprecationRegistry`/`DeprecatedApi`/`DeprecationStatus` (FEAT-85): a semver-aware deprecation tracker for the SDK's own public API lifecycle. Each `DeprecatedApi` entry pairs with a real `@Deprecated('...')` annotation on the code and adds structured, machine-checkable data an annotation string alone can't carry — `deprecatedInVersion`, `removeInVersion` (validated to always be after `deprecatedInVersion`), and a `migrationHint`. `DeprecationRegistry.checkAll(currentVersion)` reports each entry as `active` or `pastGrace` (removal-version boundary is inclusive); `pastGraceOnly` filters to just the ones that should already be gone. Ships with `tool/deprecation_check.dart`, a standalone `dart run` script that reads the package's own `pubspec.yaml` version and its own `kPackageDeprecations` list and exits non-zero once something is past its removal version — ready for a consumer or this repo's CI to wire in when they choose (not wired into `.github/workflows/ci.yml` by this change).
- Added `SdkHealthReport`/`HealthCollectorSpec`/`defaultHealthCollectors` (FEAT-39): a QA/support-facing diagnostic snapshot collector registry, safe to export/share by default. Each `HealthCollectorSpec` declares its own key **allowlist** — any key its `collect()` returns that isn't on that list is silently dropped (default-deny, not default-allow), so a copy-pasted `token`/secret field can't leak into a report a support person might screenshot. A collector that throws or exceeds its timeout only fails its own section (`_error`), never the rest of the report; string/list values are size-capped so a report can't balloon. `defaultHealthCollectors()` ships one collector per app/audio/performance/remoteConfig/replay-buffer module, each reporting `registered: false` (not an error) when that module isn't wired up in the consuming app. Wired into `DebugQaOverlay`'s existing debug/profile-only gate as a new "Health" tab.
- Added `RetryPolicy`/`RetryExecutor`/`RetryOutcome`/`RetryAttemptEvent` (FEAT-35): a reusable exponential-backoff-with-jitter retry for cloud save/config/analytics calls, so consumers stop hand-rolling delay loops. `RetryPolicy` is pure math (immutable, computed entirely in `double` microseconds so a huge attempt number clamps to `maxDelay` instead of overflowing); `RetryExecutor` runs the actual loop with injectable `delayFn`/`randomFn` (same seam-injection convention as `HapticChoreographer`'s `createTimer`), so tests drive it deterministically without real delays. `retryIf` lets a caller stop immediately on a non-transient error; `isCancelled` lets a caller abort mid-loop; the final failure's `cause`/`stackTrace` are always preserved, never swallowed.
- Added `SecureStorageAdapter`/`SecureStorage`/`FakeSecureStorageAdapter` (FEAT-40): a platform-neutral secure-storage seam (no concrete SDK pulled in — a consumer registers their own adapter, e.g. wrapping `flutter_secure_storage`) with no `Noop*` default on purpose, same reasoning as `PurchaseSeam` — silently no-op'ing a secret write would hide a real integration bug. `SecureStorage.read/write/delete/clear` add the typed `SdkResult` contract, key validation, and — critically — a clear typed failure when no adapter is registered rather than ever falling back to plain `StorageService`/SharedPreferences for something meant to be secret. `FakeSecureStorageAdapter` is an in-memory test double for consumer contract tests.
- Added `GameTimeController`/`GameClock` (FEAT-49): a gameplay clock kept separate from wall clock, so pause/slow-motion/replay never desyncs a game's own timers. `GameClock` is a pure, no-Flutter-dependency core (mirrors `PerformanceTierService`'s `FrameBudgetTracker` split) — `advance()` clamps a negative or huge (backgrounded-for-minutes) delta, applies `scale` (rejecting a non-finite/non-positive value without touching the existing scale), and supports an optional fixed-step accumulator for deterministic sub-stepping. `GameTimeController` bridges it to Flame's `update(dt)` loop via `tick()` and to Flutter via the `elapsed` `Rx`; when a `GameSessionController` is wired in, ITS pause state is the sole authority (no second, competing pause flag), so double pause/resume between systems can't happen.
- Added `CheckpointCoordinator` (FEAT-46): coalesces multiple game systems' state into one atomic, versioned save checkpoint on top of `StorageService` — one JSON blob under one key, so a commit can never be observably "half applied" across participants the way separate per-system keys could be if killed mid-sequence. `requestCheckpoint()` debounces frequent calls (position/score ticks) into one flush after a quiet window; `critical: true` cancels that debounce and flushes immediately. A `RoyLifecycleCoordinator` hook flushes immediately on backgrounding. Keeps the previous commit as a fallback generation — `restoreLatest()` tries the current commit first, then that fallback, so one corrupted write doesn't lose the whole checkpoint; a participant's `snapshot()` throwing (or a non-JSON-encodable aggregate) aborts the whole flush before anything is written, never a partial/mixed commit.
- Added `AsyncCommonButton` (FEAT-50): a `CommonButton` wrapper that drives itself through idle/loading/success/error around an async `onPressed` — the state machine `BackupRestorePanel` hand-rolled per-widget before this existed. Guards double-tap/re-entry, supports an optional `timeout`, auto-reverts to idle after `successDuration`/`errorDuration`, respects `NeonTheme.reducedMotion`.
- Added `RewardTransactionPipeline`/`RewardLine`/`RewardTransactionRecord`/`RewardSource` (FEAT-42): orchestrates a reward grant (ad/IAP/quest/daily-login) across multiple currency lines on top of `EconomyWallet`'s existing per-line idempotency — groups lines under one logical transaction id (each line gets its own derived wallet transaction id so 2 lines never collide), keeps a source-tagged persisted audit trail, and `resumePending()` finishes a multi-line grant interrupted mid-way. A post-commit analytics hook can never roll back an already-applied reward. Earn-only by design; `grantFromDailyQuest`/`grantFromDailyLogin`/`grantFromPurchase` are thin adapters over the generic `grant()`.

- Added `SaveSlotManager`/`SaveSlotMeta` (IDEA-56): manages multiple independent save slots (separate characters/profiles) on the same device — `createSlot`/`listSlots` (most-recently-played first)/`renameSlot`/`touchSlot` for metadata, `activeSlotId`/`setActiveSlot` for which slot is current, and `keyFor(slotId, suffix)` handing out a namespaced storage key for a caller's OWN `VersionedJsonStore` (this never defines the player-profile schema itself). `deleteSlot` removes a slot's metadata and every one of its namespaced keys via `StorageService.removeAllWithPrefix` — no leftover keys, and it becomes the new `activeSlotId: null` if it was the active one.

- Added `SeededRandom`/`RandomSnapshot`/`CompiledWeightedTable`/`SeededRandomService` (FEAT-45): a deterministic, cross-platform-stable RNG — `SeededRandom` implements `dart:math`'s `Random` (so it's a drop-in source for `weightedRandomPick`/`List.shuffle`/anything else expecting a `Random`), but unlike it exposes its internal state via `snapshot()`/`SeededRandom.fromSnapshot` for exact resume, and uses hand-rolled 32-bit-safe arithmetic so the same seed + call sequence produces the same output on every Dart compile target (a naive 64-bit generator would silently drift between the VM and a web build). `SeededRandomService` derives independent, namespaced streams (`stream('loot')`, `stream('enemy_spawn')`, ...) from one root seed via FNV-1a, so one system calling its stream an extra time never shifts another system's sequence. `CompiledWeightedTable` pre-validates a loot table once instead of every `pick()` call.
